# TelyClaw

> 一句话：**盯住一批人 → 抓出他们正在聊什么 → AI 帮你写成能直接发的帖子。**

> 这是一个 MVP，为「Growth Lead / Vibe Coding Challenge」而做。当前**不接入真实 X API**，但取数层、发布层都做了接口抽象，填入凭证即可切换到真实数据。

## 1. 快速开始

**方式一：双击 `start-telyclaw.bat`**（Windows）。脚本会自动找 Python、装依赖、检查端口、打开浏览器。

**方式二：命令行**

```bash
cd telyclaw
pip install -r requirements.txt      # 只有 3 个：fastapi / uvicorn / requests
python app.py
```

浏览器打开终端里打印的地址（默认 `http://127.0.0.1:8765`）。

**要让 AI 功能生效**：打开「设置」页，填一个 DeepSeek API Key。不填也能跑——取数、聚类、打分、榜单照常出，只是没有 AI 的话题名、摘要、排名理由和写稿。

> 开发环境 Python 3.13。依赖很轻，其他 3.x 版本大概率可用，但只在 3.13 上实测过。

## 2. 产品逻辑（Product Logic）

### 要解决什么

一个做增长的人，每天面对的问题是：**该发什么**。

现有的两条路都不好用：盯着时间线刷，靠手感，不可复现；看第三方热榜，那是全平台的热，跟你账号的定位无关。

TelyClaw 想补上中间那一环：**先确定「我该盯谁」，再在这些人的讨论里找出「正在起来、和我相关、还没被说烂」的话题，最后把这个话题变成一条能发的帖子。**

### 完整链路

```
选账号 → 选时间窗口 → 抓帖子 → 内容安全检查 → 聚成话题 → 九维打分排名
                                                              ↓
                                            AI 选 3 个最值得跟进的（人可改）
                                                              ↓
                                            每个给 3 个内容角度 → 每个角度 3 条帖子 → 编辑 → 发布
```

### 三个刻意的设计选择

**一、聚类用确定性算法，不用 LLM。**

热点是"几条帖在讲同一件事"这件事本身，用关键词共现就能算出来，而且**同样的输入永远得到同样的结果**——演示时刷新页面榜单不会乱跳。LLM 只负责"这叫什么、在吵什么"这一层需要语义理解的判断。

代价：遇到跨语言的同义表述（"推理成本"和 "inference cost"）聚类会分开。我当时判断这个代价值得付，因为可复现性对演示更重要。

**二、AI 不参与时，系统照常能用。**

取数、聚类、打分、榜单这四个环节完全不依赖 AI。AI 挂了只是没有话题名和文案，核心功能不瘫。这不是"降级方案"，是我从一开始就把 AI 定位成**增强层**而不是**依赖层**。

**三、绝不用预写内容冒充 AI 输出。**

AI 失败时，界面上出现的只有"AI 这次响应超时了，可以重试"和一个重试按钮。**不会**出现一段看起来像 AI 写的、其实是写死在代码里的文字。这个选择在演示场景是有风险的（万一当场挂了会尴尬），但假内容一旦被识破，整套东西的可信度就没了。

## 3. 系统架构（System Architecture）

```
┌──────────────────────────────────────────────────┐
│  浏览器（原生 HTML/CSS/JS，零构建，不需要 npm）      │
│  设置 | 监控 | 内容工作台 | 发布记录                 │
└───────────────────┬──────────────────────────────┘
                    │ 本地 HTTP
┌───────────────────▼──────────────────────────────┐
│  Python 服务（FastAPI）                            │
│                                                    │
│  ┌──────────┐  ┌───────────┐  ┌────────────────┐ │
│  │ 检测流水线 │  │ 内容流水线 │  │ 账号/草稿/记录   │ │
│  └────┬─────┘  └─────┬─────┘  └────────────────┘ │
│       │              │                             │
│  ┌────▼──────────────▼──────┐  ┌────────────────┐ │
│  │ 取数层 PostSource         │  │ 发布层 Publisher│ │
│  │  · MockSource（默认）     │  │  · Mock（当前） │ │
│  │  · PasteSource            │  │  · X（预留）    │ │
│  │  · XApiSource（预留）     │  └────────────────┘ │
│  └───────────────────────────┘                     │
│  ┌───────────────────────────┐  ┌────────────────┐ │
│  │ AI 层（DeepSeek，写死）    │  │ 存储：本地 JSON │ │
│  │  安全检查/命名/排名/角度/写稿│  └────────────────┘ │
│  └───────────────────────────┘                     │
└────────────────────────────────────────────────────┘
```

**核心原则：凡是"将来要换成真的"的地方，现在都留一个接口。**

取数、发布、AI 三处都是「接口 + 至少一种实现」。换实现只改配置，业务代码一行不动。这不是为了显得设计得好，是因为我很清楚这个 MVP 里最可能被替换的就是这三处。

**为什么是本地服务 + 本地 JSON，而不是云端 + 数据库：**

这是 MVP，判断标准是"能不能在面试里从头点到尾讲清楚"。本地方案省掉了部署、鉴权、数据库连接这一整层——它们对演示这个核心目标没有任何贡献，但会消耗掉大量时间，并且引入一堆新的失败点。代价是没有多用户、不能远程访问，这些在限制里如实列出。

## 4. 热点识别逻辑（Trend Detection Logic）

分两段：**先确定性处理，再交给 AI**。

### 4.1 确定性处理（`core/keywords.py` + `core/cluster.py`）

1. 按时间窗口过滤帖子
2. 抽标签：`#hashtag` 直接当强信号；英文正文去停用词后统计词频与相邻两词组合；保留全大写缩写（AI / LLM / MCP / RAG / API…）
3. **两级聚类**：
   - **一级**：帖子里的 hashtag 够多时（≥3 个不同标签、覆盖 ≥50% 帖子），**直接用 hashtag 聚类**。标签是作者自己写的"这条在讲什么"，信号最干净。两个标签的共现重合度 = 交集帖子数 ÷ 较少那个的帖子数，≥0.5 就合并。
   - **二级**：hashtag 不够时（粘贴导入的帖子经常没有标签），退回**关键词共现聚类**：新标签的帖子被已有簇覆盖 ≥75% 就并入；一个簇 ≥70% 的帖子都在更大的簇里就丢掉（去重）；最终上限 12 个话题。
4. 丢弃成员 <2 条的簇（噪声）

> **踩过的坑值得说一下**：最早只有二级策略。结果通用词（model、nobody）横跨多个话题，把簇全粘在一起——8 小时窗口炸出 51 个话题，名字还是 "nobody" 这种噪音词。所以改成两级，hashtag 优先。

### 4.2 AI 处理（`ai/tasks.py`）

把粗簇打包成**一次**请求发给 DeepSeek，让它输出话题名、一句话摘要，以及三个 0~100 的内容性分数（玩梗 / 搞笑 / Drama）。

### 4.3 升温程度怎么算的

题面 Bonus 里有一项 "Trend Velocity / Momentum Detection"，我把它做进主公式了，占 10% 权重：

```
升温倍数 = (最近 1/4 窗口内的提及占比) ÷ 0.25
```

24 小时窗口里如果 60% 的帖子集中在最近 6 小时，就是 0.6 ÷ 0.25 = 2.4 倍。

关键是**小样本收缩**：`实际倍数 = 1 + (原始倍数 - 1) × min(1, 帖子数/6)`。不做这一步，一个话题只要有 2 条帖子、恰好都在最近时段，就会被判成"暴涨 4 倍"直接冲上第一。

## 5. 内容安全检查

**AI 逐条判定窗口内的每一条帖子，命中的只打标记、不删帖。**

### 7 类风险（`config.py` 的 `RISK_CATEGORIES`，可增删）

政治立场与选举 / 仇恨或歧视 / 暴力与灾难消费 / 色情内容 / 针对个人的恶意攻击 / 未经证实的严重指控 / 明显违法或欺诈内容

### 为什么只打标记不删

因为"风险"在内容运营里从来不是技术问题，是**判断问题**。

一个科技账号该不该蹭一个有政治争议的话题？这取决于品牌调性、当时的舆论环境、法务的意见——AI 判断不了，我也不该替运营的人决定。所以系统做的是：**把风险明确标出来，把话题留在榜上，把决定权交回给人。**

具体做三件事：

1. 命中的帖子在话题卡片顶部显示 `⚠️ 这个话题里有 N 条被判为风险内容：xxx`，风险帖本身标红
2. AI 的 Top 推荐 prompt 里写死：`risk_count > 0` 的话题一律不选
3. 界面顶部显示检查状态，**没检查就是没检查**，不许假装检查过：

| 状态 | 界面显示 |
|---|---|
| 已检查，命中 | ✅ 已用 AI 检查 N 条帖子，标记出 M 条风险内容、涉及 K 个话题 |
| 已检查，没命中 | ✅ 已用 AI 检查 N 条帖子，未发现风险内容 |
| 未执行 / 失败 | ⚠️ **未执行安全检查** —— 本榜单没有任何风险标记，别直接拿去发帖 |

### 两个实现细节

- **不用关键词黑名单**。黑名单漏判率高，还会把正常的技术争论误杀（"这个模型就是垃圾"会被"仇恨"规则命中）。prompt 里明确要求"只判明确命中的，正常的产品吐槽、商业批评、行业分歧不算风险"。
- **一次调用批量判定全部帖子**（每批 50 条），不是逐条请求。

配置里还有一个 `exclude_risky` 开关（默认 `false`），改成 `true` 才真正把风险帖从聚类中剔除——给"确实要硬过滤"的场景留的口子。

## 6. 机会排名逻辑（Opportunity Ranking Logic）

九个维度各自在**当前窗口内**做归一化（最高的 100 分，最低 0 分），再加权求和：

| 维度 | 权重 | 谁算 | 为什么要有它 |
|---|---|---|---|
| 互动总量 | 20% | 规则 | 区分"有人聊"和"聊得很热" |
| 参与账号数 | 20% | 规则 | **防止一个人刷屏霸榜** |
| 提及量 | 15% | 规则 | 最直接的"有多少人在聊" |
| 新鲜度 | 15% | 规则 | 让突发话题冒头，不被慢热话题占死 |
| 升温程度 | 10% | 规则 | 抓"正在起来"的，不只是"已经很大"的 |
| 玩梗潜力 | 5% | AI | 能不能被做成梗、段子、二创 |
| 搞笑度 | 5% | AI | 有没有幽默、反差、荒诞感 |
| Drama 程度 | 5% | AI | 观点分歧和火药味（越强越容易引发回复转发） |
| 未饱和机会 | 5% | 规则 | 人多帖少 = 刚扩散开还没被消费完 |

**未饱和**用的是反向指标：`账号数 ÷ 提及数 × 100`。人少帖多说明是少数账号在刷屏；人多帖少说明话题刚铺开、还没被消费完——后者才是机会。

### 三个容易踩的坑，这里说清楚

**一、AI 打分的三维度必须在拿到 AI 结果后重算一次分。**

这是实现里最容易漏的一步。流程是「聚类 → 打分 → AI 命名 → 排名」，但玩梗/搞笑/Drama 是 AI 在命名那一步才给的。如果不在拿到之后再调一次打分，这 15% 权重等于完全没生效——数字会看起来很正常，实际是死权重。

**二、AI 没参与时三维度取中性值 50，不是 0。**

全部话题取值相同 → 归一化后全是 100 → 对排序零影响，同时界面上如实标注"未打分"。取 0 会导致 AI 参与的场次和没参与的场次排名逻辑不一致。

**三、分数只在同一次检测、同一个窗口内可比。**

"过去 3 天"累积的互动量天然远大于"过去 1 小时"。这是归一化方式的必然结果，不是 bug。界面上始终标注当前窗口，切窗口时整张榜单重新计算。

## 7. 内容生成逻辑（Content Generation Logic）

```
选一个热点 → AI 给 3 个内容角度 → 点一个角度 → AI 给 3 条不同风格的帖子 → 选一条编辑 → 发布
```

**角度**固定为三类，每个都给"为什么这个角度有价值"的理由，界面上有类型标签：

| 类型 | 含义 |
|---|---|
| Hot Take | 反共识，有明确立场，说别人没说或不愿说的 |
| Educational | 把这个话题讲清楚，做科普或拆解，给读者信息增量 |
| TelyClaw Product Angle | 用热点当切入点，讲它印证了什么痛点、TelyClaw 在什么场景下能解决 |

第三类是题面明确要求的，也是最容易写砸的一类——写成了广告就没人看。Prompt 里的约束是"像在聊行业顺带提到产品，不要硬广、不要罗列功能、不要出现『快来试用』"。

**帖子**三种风格：犀利观点型（先抛结论）/ 数据清单型（编号列要点）/ 提问互动型（问题开头引导回复）。用英文写，每条 ≤260 字符留出编辑余量，最多带 1 个 hashtag，不编造具体数字。

### 一条硬红线：不许只是转述原帖

蹭热点的帖子最容易犯的毛病，就是把原帖换个说法重讲一遍——那对读者没有任何价值。所以写稿 Prompt 里有一条加粗的红线：

> 绝不能只是转述、改写或总结原帖。每条帖子都必须给出原帖里没有的东西：一个明确立场、一个分析框架、一条可执行的建议，或一个反常识的追问。
> 自检标准：如果读者只看原帖就能得到这条帖子的全部信息，那这条就不合格。

为了让这条约束可验证，AI 还要为每条帖子填一个 `value_add`：**这条帖子相对原帖新增了什么**，界面上直接显示在正文下面。评审不用自己判断，看这一行就知道 AI 有没有真的加东西。

另外，角度类型是 product 时，3 条里至少 1 条必须自然出现 TelyClaw。模型偶尔会偷懒不写，所以代码里加了一道兜底：**生成完先检查，一条都没提到就再要一次**（仍然是真实 AI 调用，不用预写内容顶替）。

**人在哪里把关**：

- AI 推荐 Top 3 之后，人可以把任何一个换成榜单上的其他热点
- 3 个角度由人选，不是自动选第一个
- 3 条帖子由人选，选完进编辑框还能改
- 点"发布"会先弹一个 X 样式的预览卡片，确认后才写入记录

这套"AI 出方案、人做决定"的设计贯穿全流程。原因很简单：**内容是发在品牌账号上的，AI 不承担后果，人承担。**

### 关于"值不值得跟进"

设置页有一项「TelyClaw 账号定位」（默认：面向独立开发者与早期创业者的 AI 内容增长工具）。AI 推荐 Top 3 时不只看热度，还要给出契合度理由，并且要提到定位里的具体人群或场景。

**没做的**：契合度目前是定性理由，**没有量化成分数**进排行榜。也就是说排行榜排的是"这个话题有多热"，不是"这个话题对我多有用"。这是当前最明显的一个缺口，在限制里列了。

## 8. 投入生产后的数据获取方案

题面第 2 页问的是：如果真正投入 Production，你怎么解决数据获取问题。

### 先说约束，因为约束决定了架构

截至 2026 年 9 月（**X 的定价调整频繁，以下数字以官方最新页面为准**）：

| 事实 | 影响 |
|---|---|
| 免费层是**写优先**，几乎没有读取能力 | 生产环境不可能用免费层取数 |
| 2026 年 2 月 X 把计费从纯月费档改成了「月费 + 按资源单价 + 月度硬上限」 | 成本模型变了，不能再按"月费包月随便调"来设计 |
| 自助档（Basic / Pro）有约 **2,000,000 次/月**的读取硬上限 | **这是最硬的一条**。超过就必须走 Enterprise（公开资料约 $42,000/月起） |
| 按资源单价约 $0.005/次读取（超额部分） | 每一次读取都是真金白银 |
| 同一资源在同一 UTC 日内的重复读取**不重复计费** | 缓存和去重能直接省钱，不只是省时间 |
| 全量归档搜索、Filtered Stream 需要 Pro 及以上 | "更早发现"这件事的能力是分档卖的 |

> 说明：我在查资料时发现不同来源对 Basic 档的月费和包含额度说法不一致（$100 还是 $200、1 万还是 200 万次）。**上面只写多个来源一致的部分**；涉及具体选型时，我会去官方页面重新核对，而不是拿二手数据做预算。

### 结论：读取量必须当成成本来设计

这直接决定了架构，而不是"先做出来再优化"：

**一、固定名单，不做全量。**

监测 50~200 个高信号账号，而不是铺几千个。理由不是"少即是多"这种美学判断，是算术：500 个 KOL × 每天轮询 3 次 × 30 天，光时间线就是 4.5 万次/月，再加上拉每条帖子的回复和转发，很容易冲到 200 万次以上撞上限。

而"监测名单的质量"本身就是这个产品的核心资产——**用 200 个选得准的账号，比用 2000 个随便选的账号得到的信号更好，成本还低一个数量级。**

**二、增量拉取，不重复取历史。**

用 `since_id` + `pagination_token` 只取新帖。历史数据一次性回填，不进日常轮询。

**三、缓存与去重。**

利用"同一资源当天重复读免费"这条规则：用户 ID 映射永久缓存；帖子内容按 ID 去重；界面多次访问同一热点不重复请求。这一层不是优化，是成本控制。

**四、能用推送就不用轮询。**

Account Activity API / Filtered Stream 是事件驱动的，只有真有新内容时才计费。对"更早发现热点"这个目标，推送在时效性和成本上都优于轮询。**但要注意反向的账**：被别人 @、收到 DM 这类**入站事件也是计费的**（公开资料约 $0.005~$0.010/事件）。一个活跃的账号光收私信就可能产生一笔不在预算里的账单。所以订阅推送前要先估入站事件量。

**五、分层降级。**

```
官方 API v2（默认路径）
   ↓ 用量超过自助档上限
Enterprise 合同，或官方授权的数据转售商
   ↓ 都不可行
缩小监测名单 / 降低轮询频率（保住核心信号，而不是全量降级）
```

**明确不做的事**：不用浏览器自动化、不用非官方端点、不绕过付费墙。这类做法会有封号风险，且违反 X 开发者协议——对一个代表品牌官方账号的工具来说，这个风险不可接受。

### 工程上还要补的

- **存储换 Postgres**，帖子表按 `created_at` 分区 + 索引。现在的本地 JSON 在几十万条量级就会撑不住
- **速率限制与退避**：读 `x-rate-limit-remaining`，接近上限主动减速；遇到 429 睡到 `x-rate-limit-reset` 再做指数退避
- **成本可观测**：每次读取计费，所以要有用量看板，能按账号/按天看到调用量和预估成本，超阈值告警
- **取数失败可重试**：现在是同步拉取，生产环境要换成队列 + 重试

## 9. 数据说明与切到真实 X API

### 现在的数据是模拟的

**这一点必须说清楚：界面上所有帖子内容都是 AI 生成的模拟数据，不代表任何真实用户的言论。** 页面顶部有常驻的黄色横幅标注。

内置 92 条种子数据：87 条正常内容 + 5 条**刻意混入的风险内容**——因为不混进去，内容安全检查在演示时永远是"0 条命中"，等于功能是隐形的。

那 5 条风险内容**只挂在 3 个虚构账号名下**（`dailyrant_err` / `hot_take_247` / `thefeed_anon`，显示名都带"示例号"），**没有一条放在真实 KOL 名下**。这是刻意的：把伪造的政治言论或欺诈内容挂在真人头上，是这个项目里我唯一觉得不能越的线。

另外 6 个账号是真实的科技/AI 领域 KOL 账号名（sama、karpathy、ylecun、paulg、naval、levelsio）。用真人名字是因为演示需要可信的语境，但**他们名下的所有内容同样是模拟生成的**，界面全程标注。

**时间戳是相对生成的**：种子里每条帖子只记"距现在多少分钟"，取数时才换算成真实时间。否则你晚上演示时选"过去 1 小时"会一条都查不到。同理，1 小时窗口内刻意铺了 6 个话题簇，保证最小窗口也能聚出足够的话题。

### 怎么切到真实 X API

取数层是一个接口 + 三种实现：

```python
class PostSource:
    def fetch(self, handles: list, since, until) -> list[Post]:
        """取回指定账号在时间区间内发布的帖子"""
```

改配置里的 `source` 一行即可：`mock`（默认）/ `paste` / `x_api`。

`sources/x_api_source.py` 里接口和返回结构都已定义好，字段映射函数 `map_tweet()` 也写好了（把 X 返回的 `public_metrics` 映射成 `Post`）。要真正启用，只需要：

1. 在设置里填 `x_bearer_token`（读）
2. 在 `fetch()` 里补上三步真实请求：用户名换 user_id → 按时间范围取推文 → 映射成 Post

用到的 X API v2 端点：

| 需要的能力 | 端点 |
|---|---|
| 用户名 → 用户 ID | `GET /2/users/by/username/{username}` |
| 批量取用户 | `GET /2/users?usernames=a,b,c` |
| 取某用户推文 | `GET /2/users/{id}/tweets`（带 `start_time` / `end_time`） |
| 发布 | `POST /2/tweets` |

未配置凭证时，界面明确提示"尚未接入真实 X 数据"，不会悄悄失败。

**发布层同理**：`Publisher` 是一个类，当前只有模拟实现（写本地记录 + 复制到剪贴板）。换真发布只需要新增一个实现调 `POST /2/tweets`。

## 10. 用了哪些 AI / Vibe Coding 工具

诚实交代，不美化：

- **WorkBuddy**（AI 编程助手，IDE 内 agent 模式）—— 整个项目的代码由我和它结对完成。我用它做架构设计讨论、代码生成、以及反复的调试（比如话题聚类从 51 个爆炸到稳定在 6~12 个，是几轮对话调出来的）
- **DeepSeek**（`deepseek-chat`，OpenAI 兼容格式）—— 产品内所有 AI 能力的提供方，写死在 `config.py` 里
- **FastAPI + 原生前端** —— 没有用任何前端框架和构建工具

**AI 在这个项目里做了什么、没做什么：**

- 做了：生成样板代码、帮我把模糊的想法变成可执行的结构、调试时快速定位问题、帮我发现自己前后矛盾的设计
- 没做：**没有替我做产品判断**。权重怎么定、风险内容该删还是该标、AI 失败时该不该用假内容顶上——这些是我拍板的，也是这份文档里我花最多篇幅解释的部分

我特意保留了几个"AI 很容易顺手做掉、但做错了会很糟"的地方作为人工检查点：不用预写内容冒充 AI 输出、安全检查只打标记不删帖、每个版本的分数口径必须自洽。

## 11. 当前 MVP 的限制

分两类。**"没打算做"是范围选择，"做了但有缺陷"是真的弱**——后者才是需要交代的。

### 11.1 设计上就没打算做的

| 限制 | 原因 |
|---|---|
| 数据是模拟的 | 题面明确说 MVP 不需要真实 X API |
| 发布是模拟的 | 同上。接口已预留，填凭证即可真发 |
| 手动触发检测，没有定时任务 | 演示节奏可控，不会因为定时刷新打乱讲解 |
| 没有多用户、登录、鉴权 | 本地单人工具的 MVP，加这些不产生演示价值 |
| 没有云端部署 | 同上 |
| 数据存本地 JSON | 几十万条以内够用，换 Postgres 是生产化的第一步 |
| 没有历史趋势追踪 | 每次检测覆盖上一次结果，看不到话题热度随时间的变化 |
| 没有发布后的效果回流 | 已发布内容没有互动数据回填，无法证明"哪个热点真的带来了增长" |

### 11.2 做了但有缺陷的

**一、关键词抽取只覆盖英文。**

`core/keywords.py` 的分词正则只匹配 `[A-Za-z]`。中文帖子如果没有 `#标签`，几乎抽不出关键词，二级聚类会直接退化成空（成员 <2 条的簇会被丢弃）。AI 命名和摘要是中文的、不受影响，但聚类这一层会失效。

要做中文，得换成 jieba 之类的中文分词，并且 hashtag 优先的一级策略需要相应调整。这是当前**技术上最大的短板**。

**二、内容安全检查是 AI 判断，不是规则。**

会误判（正常的技术争论被标成攻击），也会漏判。而且同一个输入两次跑，结果可能不完全一致。所以界面上才必须显式区分"已检查 / 未检查"——**标了安全不代表真的安全，最后一道关是人**。

**三、AI 调用是串行的，一次检测约 10~15 秒。**

4 次调用依次执行：安全检查 → 命名与摘要 → 排名理由 → Top 精选。实测 11~15 秒。演示时能接受，但如果这是日常工具，这个延迟会让人不想用。可以并行化（安全检查和命名之间没有依赖），也可以缓存。

**四、分数只在同窗口内可比。**

这是归一化方式的必然结果，不是 bug，但确实容易被误读成"24 小时窗口的第一名比 1 小时窗口的第一名更热"。界面上标了，但不够醒目。

**五、契合度没有量化。**

"值不值得 TelyClaw 跟进"只在 Top 精选那一步用 AI 定性判断，没有变成一个可排序的分数。所以排行榜排的是热度，不是机会。

**六、模拟数据是固定种子生成的。**

92 条，内容写死。有"换一批数据"按钮，但只是重新抖动互动数和措辞，话题结构不变。演示够用，不能用来验证算法在真实数据上的表现。

## 12. 如果有更多时间与资源

按"对增长目标贡献最大"排序，不是按实现难度：

**1. 效果回流闭环（最重要）**

现在这套系统能证明"我发了很多内容"，不能证明"这些内容有效"。补上发布后的互动数据回填，才能算出**热点命中率**——哪个热点真的带来了 qualified engagement。有了这个数，才能反过来优化权重。

这是从"内容工具"变成"增长系统"的分界线。

**2. 历史趋势追踪**

把每次检测的结果存下来，就能看到话题热度随时间的变化曲线。这样"升温程度"可以从窗口内的统计推断，升级成真正的跨时间对比——也就能回答"我们比别人早多久发现这个话题"。

**3. 契合度量化**

把"值不值得跟进"变成排行榜里的一个维度，而不只是 Top 精选时的一句理由。

**4. 中文支持**

换中文分词，让聚类在非英文内容上也能用。

**5. TelyClaw 产品角度**

题面在内容角度里明确列了三类（Hot Take / Educational / **TelyClaw Product Angle**），现在 AI 是自选的，缺了强制的产品角度——而这一条恰恰是"蹭热点"和"蹭热点但带上自己"的区别。

**6. 生产化**

Postgres、队列化取数、用量看板与成本告警、鉴权与多用户、部署。
